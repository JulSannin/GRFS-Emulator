# GRFS-Emulator

Свой сервер Quazal Rendez-Vous для Ghost Recon: Future Soldier (ПК). Написан с нуля на Python,
без зависимостей. Официальные серверы игры Ubisoft отключила 25.01.2024.

Проект не трогает игру: ни патчей, ни подмены DLL, ни хуков в процесс. Нужна легальная копия,
привязанная к аккаунту Ubisoft, — пароль Ubisoft проверяет Ubisoft, а не этот сервер.

## Запуск

Для Windows есть сборка из двух приложений: `GRFS-Server.exe` и клиентский лаунчер
`GRFS-Client.exe` с вводом IP сервера. Python на компьютерах игроков не нужен.
Сборка — `build_windows.bat`; результат — `dist/GRFS-Windows-x64.zip`.
Порядок запуска и настройки: [инструкция для Windows](docs/WINDOWS.md).

```powershell
cd "D:\Steam\steamapps\common\Tom Clancy's Ghost Recon Future Soldier\GRFS-Emulator"
python -m grfs
```

Нужен Python 3.11+ (проверено на 3.14). Больше ничего ставить не надо.

Поднимутся пять слушателей и строка `ready:` со всеми портами:

| | |
|---|---|
| TCP 80 | служба конфигурации — игра спрашивает её первой |
| UDP 21030 | сервер аутентификации (вход, тикеты) |
| UDP 21031 | защищённый сервер (всё остальное) |
| UDP 21032, 21033 | определитель типа NAT (`punch_port` и следующий за ним) |
| TCP 8080 | [страница состояния](http://127.0.0.1:8080/) |

Если на машине с сервером включён файрвол, открыть надо все UDP-порты из таблицы, включая 21033.

На **каждой** машине, которая играет, нужна строка в `C:\Windows\System32\drivers\etc\hosts`:

```
127.0.0.1       onlineconfigservice.ubi.com     # на самой машине с сервером
192.168.1.8     onlineconfigservice.ubi.com     # у остальных: адрес машины с сервером
```

Настройки — `grfs.ini` (шаблон: `grfs.ini.example`), переменные `GRFS_*` или ключи командной
строки (`python -m grfs --help`). Менять там обычно нечего.

**Адрес, который сервер сообщает клиенту, нигде не задаётся.** Он определяется по тому, откуда
клиент пришёл: игре на этой же машине — `127.0.0.1`, игре по сети — тот наш адрес, который до неё
достаёт (это знает сама ОС). В предыдущей попытке этот адрес брался из настроек, и при `bind`
`0.0.0.0` каждому клиенту сообщалось `address=0.0.0.0`; игра молча не регистрировалась и уходила
в офлайн. Настройка `advertise` есть только для случая, когда перед сервером NAT.

### Настройки, которые может понадобиться менять

| | |
|---|---|
| `punch_port` (`--punch-port`) | порт определителя NAT, по умолчанию 21032; занимает и следующий. `0` — выключить |
| `news_title`, `news_body` | одно сообщение в панели новостей главного меню; по умолчанию пусто |
| `generic_settings` | переключатели `GetGenericSettings`, например `2=20, 0=2026-12-24, 1=2026-12-27 06:00` — двойной опыт между двумя датами (`grfs/services/misc.py`) |
| `auto_friends` | все на сервере — друзья всех; по умолчанию `no` |
| `twin_logins` | вторая копия игры под тем же аккаунтом — отдельный игрок `<имя>_2`, а не замена первой (см. «Две копии игры на одной машине»); по умолчанию `no` |
| `data_dir` (`--data-dir`) | где лежат аккаунты, друзья, кланы и статистика; по умолчанию `data` в папке проекта |

**Определитель NAT.** Тип NAT, который игра показывает и по которому решает «Unable to join due
to STRICT NAT», она узнаёт одним способом: модулем Storm punch, адреса которого берутся из ключа
конфигурации `punch_DetectUrls`. Служба Ubisoft этот ключ не отдавала, и тип оставался Unknown.
Здесь ключ указывает на два порта самого сервера, и любой игре отвечают так, что она видит Open
(почему именно так — `grfs/punch.py`). С `punch_port = 0` ключа нет, тип снова Unknown.

**Online pass.** В конфигурации есть ключ `PassportKillSwitch`: клиент проверяет только его
наличие и, если он есть, не ищет привилегию онлайн-пропуска. Без него игра не пускает к поиску
сессий тех, у кого пропуска нет, а выдать его здесь некому.

## Проверка без игры

```powershell
python tools\fake_client.py --config              # сервер на этой машине
python tools\fake_client.py --host 192.168.1.8    # сервер на другой машине
python tools\fake_client.py --nat                 # ещё и NAT-проба
python tools\fake_client.py --friends             # ещё и двое игроков становятся друзьями
```

Скрипт проходит тот же путь, что игра: рукопожатие, вход, запрос тикета, рукопожатие с защищённым
сервером (с доказательством, что тикет прочитан), регистрация адресов, NAT-проба. Печатает каждый
шаг. Это то, чего не было в предыдущей попытке: каждая проверка стоила запуска игры, взгляда в меню
и догадки, какая из двух машин виновата.

Ожидаемый вывод — все строки с `+` и `everything answered`.

Второй игрок, которым управляешь руками (одна настоящая игра с одной стороны, это — с другой):

```powershell
python tools\fake_game.py --name bob                       # сервер на этой машине
python tools\fake_game.py --name bob --host 192.168.1.8
```

Входит так же, как игра, держится онлайн пингами, печатает каждый вызов сервера к нему; изменения
в друзьях (уведомление 1000), приглашение в сессию (7005), принятие приглашения (7007) и вызов на
дуэль печатаются словами. Команды:

| | |
|---|---|
| друзья | `search`, `add`, `accept`, `decline`, `remove`, `block`, `unblock`, `list`, `invites`, `uplay`, `urls` |
| сессии | `sessions` (где я), `sessions host [PUBLIC] [PRIVATE]`, `sessions search [QUERY]`, `sessions join ID`, `sessions invite NAME [ТЕКСТ]`, `sessions invitations`, `sessions accept-invite [N]`, `sessions leave` |
| кланы | `clan`, `clan create ИМЯ ТЕГ [ОПИСАНИЕ]`, `clan invite NAME`, `clan join [ID]`, `clan members [ID]`, `clan leave` |
| статистика | `stats send BOARD[/C1/C2] STAT VALUE [ADD/SUB/SET/MAX/MIN]`, `stats read BOARD [NAME]` |
| карты | `maps categories`, `maps list MASK` |
| прочее | `probe`, `ping`, `call ПРОТОКОЛ МЕТОД [JSON]`, `help`, `quit` |

P2P-стороны у него нет: настоящая игра, которая попробует войти в сессию, созданную им, ответа не
получит. Пригласить настоящую игру, принять её приглашение, состоять с ней в одном клане — можно.

### Проверка машины второго игрока

```powershell
python tools\doctor.py                         # hosts, служба конфигурации, вход, NAT echo, тип NAT
python tools\doctor.py p2p --name alice --peer bob   # на обеих машинах одновременно, игра закрыта
```

`doctor` проходит путь игры по шагам и про каждый говорит, что именно сломано и что с этим
делать: нет строки в hosts, hosts есть, а DNS-кэш старый, сервер не отвечает, адрес в
`SandboxUrl` не тот, NAT echo видит другой адрес, тип NAT Moderate/Strict. Тип NAT определяется
тем же автоматом, что в игре (`punch_DetectUrls`, P и P+1). В конце пишет `doctor-report.txt`,
без паролей. Код выхода 1, если хоть один шаг упал.

Первым делом он говорит, на какой адрес сядет UDP 2346 игры. Игра не слушает `0.0.0.0`: она
берёт первый адрес из `gethostbyname(<имя машины>)` и привязывается ровно к нему. Если первым
стоит адаптер VPN (Radmin, Hamachi, ZeroTier), игра сидит на его адресе. А Windows не отправляет
с сокета одного интерфейса на адрес другого, поэтому с сервером на 127.0.0.1 NAT-проба игры
просто не уходит. Doctor ловит это заранее и говорит, что поставить в hosts.

`p2p` — то, без чего кооператив не заведётся, а сервер не проверит: обе стороны регистрируют свои
адреса, находят друг друга через сервер и шлют пакеты напрямую с порта 2346, как игра. Итог
один из четырёх: работает в обе стороны; в одну (у кого закрыт входящий); ни в одну; второй так
и не появился. На закрытый порт подсказывает команду `netsh` для брандмауэра.

### Сборка для того, у кого нет Python

```powershell
python tools\make_bundle.py        # dist\GRFS-Tools.zip, ~11 МБ
```

Скачивает embeddable Python 3.11.9 с python.org (сверяет SHA-256, другой файл не берёт), кладёт
рядом `grfs/`, `schema/`, `doctor.py`, `fake_game.py`, `fake_client.py` и `.bat`:
`doctor.bat`, `p2p-test.bat`, `fake-game.bat`, `server.bat`. Распаковать куда угодно, запускать
двойным щелчком. Без `data/`: чужие аккаунты в архив не попадают. Это альтернатива двум `.exe`
из `build_windows.bat`: интерпретатор и исходники лежат в архиве отдельно.

### GRFS-Connect.exe для второго компьютера

```powershell
python tools\make_connect.py                        # dist\GRFS-Connect.exe, ~55 КБ, с LAN-адресом этой машины
python tools\make_connect.py --server 192.168.1.8   # с другим адресом
```

Один exe для второго игрока: скопировать к нему и запустить двойным щелчком, ставить ничего не
надо. Собирается компилятором C# из .NET Framework 4, который есть в любой Windows 10 и 11
(исходник — `tools/connect/GRFSConnect.cs`). Адрес сервера вшит как предложение по умолчанию,
можно ввести другой. Что он делает, по порядку:

1. Спрашивает у сервера конфигурацию так же, как игра, проверяет NAT echo на обоих портах PRUDP
   и определитель типа NAT. Пока это не прошло, ничего не меняется; на каждую неудачу — что
   сделать (сервер не запущен, брандмауэр сервера не пускает `python.exe`, VPN забирает адрес
   сервера в туннель).
2. Смотрит, на какой адрес игра откроет UDP 2346 (первый из `gethostbyname`, как у неё), и виден
   ли с него сервер. Если первым стоит адаптер VPN и сервер с него не виден, игру надо запускать
   этим exe: он ставит ей `_CLUSTER_NETWORK_NAME_` — адрес, с которого сервер виден, — и 2346
   садится туда. В самой игре ничего не меняется.
3. С правами администратора (тут Windows спросит): строка `<сервер> onlineconfigservice.ubi.com`
   в hosts — блоком с той же меткой, что у старого GRFSConnect, а прежние строки для этого имени
   комментируются `# (grfs)`; сброс кэша DNS; правило брандмауэра «GRFS co-op (UDP 2346-2347)»
   на входящие; по согласию — отключение запрещающих правил для игры, которые Windows создаёт,
   если в её окне про доступ к сети нажали «Отмена».
4. Предлагает запустить игру и ждёт, пока она откроет UDP 2346, — и говорит, на каком адресе.

Сам exe работает без прав администратора и просит их только для шага 3: игра, запущенная из
повышенного процесса, тоже была бы с повышенными правами, а обычно их у неё нет.

`GRFS-Connect.exe --check [адрес]` — только проверка, код выхода 1 при любой проблеме.
`GRFS-Connect.exe --off` (или `-` вместо адреса) — отключиться: блок из hosts и правило
брандмауэра убираются; строки, закомментированные при подключении, так и остаются.

Exe не упакован и ничего не распаковывает, но подписи у него нет, поэтому пришедший из интернета
или мессенджера SmartScreen встречает окном «Windows защитила ваш компьютер»: «Подробнее» →
«Выполнить в любом случае».

### Две копии игры на одной машине

Кооператив можно проверить без второго компьютера:

```powershell
# grfs.ini: twin_logins = yes
python -m grfs
python tools\launch_game.py --ip 127.0.0.1     # первая копия
python tools\launch_game.py --ip 127.0.0.2     # вторая
```

Две вещи обычно этому мешают, и обе обходятся без правки игры:

- **Порт.** UDP 2346 у игры зашит, запасного нет (`5DF010`, `5EBFF0`). Но привязывается он к
  адресу, а не к `0.0.0.0`, и адрес игра берёт из имени машины (`5DF260`). Переменная окружения
  `_CLUSTER_NETWORK_NAME_` (штатная в Windows, для кластерных служб) подменяет имя машины одному
  процессу и всему, что он запускает. Если в ней адрес, `gethostbyname` его и возвращает. Все
  адреса 127.x — эта же машина без всякой настройки, поэтому копии садятся на 127.0.0.1:2346 и
  127.0.0.2:2346 и слышат друг друга. `Future Soldier.exe` передаёт окружение дальше
  (`CreateProcessW` с `lpEnvironment = NULL`). Именованных мьютексов в игре нет: все 34
  `CreateMutexA` безымянные.
- **Аккаунт.** Имя и пароль игра получает от Ubisoft Connect (`GetLoginDetails` через Orbit),
  поэтому обе копии входят под одним аккаунтом, и обычно второй вход вытесняет первый. С
  `twin_logins = yes` вторая копия, вошедшая, пока первая жива, становится `<имя>_2` со своим
  pid. Её можно добавить в друзья, пригласить, она находит сессию первой и входит в неё.
  Псевдоним запоминается за адресом, с которого пришёл вход, поэтому после перезапуска копия
  возвращается под своим именем.

Что можно узнать только запуском: даст ли Ubisoft Connect логин второй копии, пока первая
запущена. Игра запускается напрямую, мимо Steam: Steam API в ней нет, Ubisoft Connect должен
быть запущен.

### Настоящая игра без человека у клавиатуры

`tools/rig.py` запускает свой сервер, копии игры на 127.0.0.1, 127.0.0.2…, следит за каждой по
логу сервера, снимает её окно и шлёт ему клавиши и клики:

```powershell
python toolsig.py check              # чего не хватает на этой машине
python toolsig.py up --copies 2      # сервер, затем две копии
python toolsig.py wait 1 menu        # ждать, пока копия 1 дойдёт до главного меню
python toolsig.py status             # процесс, окно, имя и пройденные шаги каждой копии
python toolsig.py shot 1             # PNG окна копии 1 в logsig\shots
python toolsig.py keys 1 down down enter
python toolsig.py click 1 640 360
python toolsig.py log --problems     # предупреждения и ошибки сервера
python toolsig.py down
```

Шаги читаются из лога сервера, а не с экрана: `signed-in`, `registered`, `nat-echo`, `menu`
(первое, что игра делает в главном меню, — просит список карт), `hosting`, `joining`,
`in-session`, `invited`, `accepted`. Копия узнаётся по адресу, с которого вошла. У рига свой
каталог данных (`logs/rig/data`) и `twin_logins = yes`: прогон не оставляет аккаунтов в `data/`.

Ввод бережёт того, кто сидит за машиной. Пока клавиатурой или мышью пользовались меньше полутора
секунд назад, окно игры не выводится вперёд и ничего не отправляется: иначе оно забрало бы чужие
нажатия. Клик не уходит, если курсор сдвинули или над точкой чужое окно. Снимок не требует
фокуса: окно без поддержки DPI `PrintWindow` рисует в своём размере, снимок растягивается до
экранного.

Один раз, от администратора, нужно то, чего риг сам сделать не может:

```powershell
powershell -ExecutionPolicy Bypass -File tools\setup_once.ps1
```

Скрипт добавляет в hosts `127.0.0.1 onlineconfigservice.ubi.com` (повторный запуск ничего не
меняет; строку с другим адресом закомментирует, а не удалит) и запускает установщик Ubisoft
Connect из папки игры, если его нет. Войти в Ubisoft Connect нужно самому: аккаунт риг не трогает.

Тесты:

```powershell
python -m unittest discover
```

потоке на свободных портах и временном каталоге данных, `grfs/fakegame.py` — клиент, который
говорит с ним по настоящим UDP-сокетам так же, как игра (окно приёма, фрагменты, повторы,
подпись на соединение). Несколько игроков в одном процессе — это несколько таких клиентов, ни
второй машины, ни виртуалки не нужно. Каждый тест в конце проверяет, что сервер не записал ни

### Друзья

Это путь к ко-опу: GRFS ищет игру друга, спрашивая, в каких сессиях сидят его контакты, — с
пустым списком друзей созданную игру найти нельзя вообще.

Работает полный цикл: FIND FRIENDS ищет по реестру аккаунтов сервера, добавление создаёт
**две стороны** (у позвавшего «Pending», у второго — приглашение), принятие делает друзьями обоих,
удаление и блокировка работают, присутствие Online/Offline берётся из активности PRUDP.

Значения отношения (1 — друг, 2 — запрос отправлен, 3 — приглашение) в схеме игры отсутствуют:
они установлены подстановкой по одному аккаунту на значение и чтением экрана. Там же два дефекта,
стоившие прогонов игры: `GetRelationships` обязан вернуть **общее число перед списком** (без него
клиент читал длину списка из первого PID и экран оставался пустым), а `byRelationship` в 11 и 12 —
это **фильтр**, а не метка для эха (иначе все друзья попадали в INVITATIONS).

Если возиться с добавлением не хочется — `auto_friends = yes` в `grfs.ini` делает всех на сервере
друзьями всех. По умолчанию выключено: обычный путь работает, а выдуманные связи мешают
разбираться, когда ломается что-то другое.

## Таблица карт

`GetMapList` отвечает ключами миров (`.wor` в bigfile), а их нет ни в одном exe — они лежат в
`Yeti.big`. Таблица уже снята в `schema/maps.json`; заново её получают так (файлы игры только
читаются):

```powershell
python tools\extract_maps.py "<папка игры>\Yeti.big"
```

Без `schema/maps.json` сервер запускается и работает, но матчмейкинговое лобби создать нельзя:
`GetMapList` отвечает ошибкой, и в логе об этом есть строка.

## Данные на диске

`data/` (или `data_dir`): `accounts.json` (аккаунты и постоянные PID), `friends.json`, `stats.json` (профили),
`clans.json`, `uplay.json`, `awards.json` и `match_keys.json` — последний выданный ключ матча,
чтобы после перезапуска, даже с часами, переведёнными назад, ключи не повторялись. Сессии и
приглашения на диск не пишутся: они живут, пока живы игры в них.

## Чего ещё нет

Всё, что клиент вызывает, отвечено. Непроверенными остаются раскладки и смыслы, снятые с кода
клиента, но ни разу не виденные с настоящей игрой: смысл значений `RichPresence`, коды результатов
кланов, биты DLC в маске карт и т. п. Они описаны в docstring'ах сервисов.

### Не отвечаем намеренно

На вызов из этого списка уходит ошибка RMC, никогда — молчание, а в логе строка

**Сервис читается как список вызовов, которые он отвечает.** Схема превращает номер метода в имя и
список параметров; обработчик — метод сервиса с тем же именем, параметры приходят именованными
аргументами. Протоколов Hermes и Overlord в схеме игры нет; их классы и методы сервис объявляет
сам (`schema_classes`, `schema_methods`) по разбору клиента, и дальше они идут через тот же кодек.
Байтовые раскладки руками нигде не пишутся, кроме одного места: у ответа `LoginEx`
живые серверы добавляли четыре байта после последнего поля, которое объявляет схема игры
(`services/auth.py`, `LOGINEX_TAIL`) — смысл неизвестен, но именно эти байты клиент принимал.

Вызов без обработчика получает ошибку RMC, никогда — молчание: неотвеченный вызов клиент повторяет
бесконечно (в одном захвате — 19 раз подряд), а ответ, принятый за значение, приводил к чтению по
нулевому указателю и падению игры.

### Правила транспорта, каждое оплачено отдельной ошибкой

* Надёжный пакет подтверждается **сразу**, а не вместе с ответом: клиент в локальной сети ждёт
  десятки миллисекунд, а запрос к диску дольше.
* Пришедший дважды надёжный пакет получает **те же байты**, что и первый, и заново не
  обрабатывается. Иначе один `CreateSession` создавал три сессии, две из которых потом
  предлагались всем в поиске.
* Ответы уходят ненадёжными — так их посылали живые серверы. Фрагменты уходят надёжными и
  нумеруются **с 1 внутри своего соединения**: клиент отдаёт их игре строго по порядку через окно,
  которое начинается оттуда.
* Состояние — у **соединения**, не у игрока. Одна игра держит их несколько с одного адреса: своё
  (виртуальный порт 15) и телеметрию (порт 14) на каждом из двух серверов, у каждого свои подпись,
  номера и ключ сессии.
* Подпись ответа — подпись того соединения, откуда пришёл запрос, и уходит он в тот же сокет.
* На Windows у UDP-сокетов сервера выключено сообщение «port unreachable» (`SIO_UDP_CONNRESET`).
  Закрытая игра оставляет порт, в который сервер ещё какое-то время пишет, Windows отдаёт ответ
  ICMP следующему чтению как ошибку, а цикл asyncio на Windows (до Python 3.12) после такой ошибки
  перестаёт читать сокет совсем: защищённый сервер глох для всех игроков сразу. Хватало одной
  закрытой игры в момент, когда сервер был занят.

### Про пароли

Игра присылает логин, online key и пароль Ubisoft в `LoginEx` и `RegisterEx`. Эти поля
**пропускаются при разборе** (`rmc/ddl.py`, `SENSITIVE`) — не маскируются после, а не читаются
вообще. Так же пропускается ключ продукта в `ActivateKey` (`secret_params` у сервиса). В логах и в
`data/` их нет, и на это есть тесты.

## Отличия от предыдущей попытки

Прошлый сервер (`D:\GRFS-Server`) — форк Phoenix на C#/WinForms. Здесь сделано иначе:

| | Там | Здесь |
|---|---|---|
| Раскладки пакетов | по классу на запрос и ответ, руками | кодек по схеме из exe |
| Состояние соединений | одна запись на адрес | на соединение |
| Лог | в окне, из сетевых потоков | stdlib logging, окна нет |
| Проверка | только запуском игры | `tools/fake_client.py`, `tools/fake_game.py`, `tools/doctor.py`, `tools/rig.py`, `GRFS-Connect.exe`, 554 теста |
| Адрес для клиента | из настроек | по endpoint'у клиента |

Все найденные там дефекты (подпись на соединение, номера фрагментов, кэш ответов, подтверждение
при приёме, слоты 5/6, формат NAT echo) учтены здесь с самого начала — в коде они помечены
комментарием, что именно ломалось.
